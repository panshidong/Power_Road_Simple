## Revision note (v2 supersedes v1)

The first implementation had two problems, found in review before any results were
finalized:

1. **Wrong destination file for power buses.** v1 used `new_bus_to_link.json` (the
   power→road *signal-dependency* mapping: "which link's traffic signal does this
   bus control") as if it were "where a crew travels to repair this bus." The
   mapping for "where the bus physically is" is `bus_location.json`
   (`interdependency.bus_loc`), a single road node per bus. v1's destinations
   were therefore pointing at the wrong object for every damaged bus.

   **Caveat (corrected after re-reading `scheduler.py`):** the base simulator's
   crew dispatch does *not* use `bus_location.json` under the default
   `bus_dispatch_mode="link_only"` inherited from Task B (see
   `TASKB_ASSUMPTIONS.md`): with `link_only`, `scheduler._candidate_nodes_for_asset`
   sends the crew to the nearer endpoint of the bus's `bus_to_link` link. So in the
   reported experiments, S3's critical-bus O–D destinations (bus physical location)
   and the simulator's crew travel target for that same bus (controlled-link
   endpoint) are two different nodes. The dispatch mode was deliberately left at the
   Task A/B default so that S0–S2 stay identical to the companion evaluations; the
   discrepancy is stated as an assumption/limitation in the paper rather than
   changed unilaterally. Switching to `bus_dispatch_mode="location_first"` is a
   one-parameter change in `task_c_runner._run_strategy` if the user wants the two
   to coincide, but it would alter S0–S2 as well.
2. **O–D set was damage-specific.** v1 built a fresh O–D set per disruption
   scenario, from crew depot to whichever assets that particular random scenario
   happened to damage. This made S3 behave like a third Shapley-style strategy
   (defined over "this scenario's damaged coalition"), not like a genuinely
   different *road-criticality scoring method* comparable to S0. S0's topological
   betweenness is a static property of the network, computed once and then looked
   up for whichever links are damaged in a given scenario; S3's road score should
   work the same way for the comparison to isolate "scoring method" as the only
   difference.

v2 fixes both: destinations for critical buses now come from `bus_location.json`,
and the O–D set is a small, **fixed, damage-independent** set of "critical"
destinations, computed once for the whole network.

## O–D scope (v2)

1) **Origin**: crew depot node(s).
   - `TaskCODConfig.depot_nodes`, default `(1,)`, matching the simulator's own
     `depot_node=1` default in `resilience_measurement.run_model_multi`.

2) **Destination set — fixed, not scenario-specific:**
   - `TaskCODConfig.critical_buses`: a small number of power buses designated
     "critical." Their destination node comes from `bus_location.json`
     (`task_c_od.load_bus_location`), matching the simulator's own crew-dispatch
     mapping.
     - Current value: `(8, 17)`, chosen by `random.Random(20260910).sample(range(1, 34), 2)`
       — a small, arbitrary, reproducible subset. The network is small (33 buses),
       so designating *all* buses as "critical" would make the concept
       meaningless; two buses were picked instead of one so the resulting O–D set
       has more than a single route to overlap against.
   - `TaskCODConfig.shelter_nodes`: road node(s) designated as critical
     facilities/shelters.
     - Current value: `(24,)`, reusing node 24 from Task B's existing
       `critical_location.json` (`[1, 24]`) rather than inventing a new node; node
       1 was excluded because it coincides with the depot.
   - These are placeholders pending confirmation; see "Where to modify later."

3) **Candidate routes per O–D pair**: `k` shortest loopless paths (Yen's algorithm)
   on the road network's static free-flow travel times.
   - `TaskCODConfig.k_paths`, default `3`.

4) **Path-rank weights**: weight applied to the 1st/2nd/3rd… candidate path when
   building the route-overlap structure.
   - `TaskCODConfig.path_rank_weights`, default `(1.0, 0.6, 0.35)` (strictly
     decreasing).

With only 3 O–D pairs (2 critical buses + 1 shelter, single depot) the resulting
route-overlap structure is sparse: in a spot check, only 14 of the network's 76
directed links carried any overlap weight, and one 4-bus/4-link scenario produced
an S3 road sequence *identical* to S0's. This is expected with such a small
critical-destination set and is exactly the kind of result the weighted-triangle
metric below is meant to help interpret — see "Two supplemental questions being
tested together," below.

## Allocation rule

- `"weighted_overlap"` (only method retained in v2): `importance(link) = sum over
  all O–D services and all candidate paths that traverse that link of that path's
  rank weight`, summed over both traversal directions (road damage is treated as
  physical two-way blockage, consistent with Task A's existing assumption). v1 also
  had an `"od_shapley"` allocation method, defined over "which damaged links are
  currently repaired" — that framing no longer applies once the O–D set is
  damage-independent, so it was dropped rather than reworked. (Per discussion,
  reconciling a Shapley-style variant of S3 is not a priority; S1 is already in the
  comparison set as the Shapley-family reference point.)

The road-side score is computed once for the *entire* network
(`task_c_od.build_static_road_importance`) and looked up for whichever road links a
given scenario happens to damage — exactly like S0's betweenness lookup. The
power-side score for `S3_od_representation` still reuses Task A's unmodified
`power_radial_service_centrality()`, unchanged from v1, to keep isolating the
road-side method change.

## Weighted-triangle supplemental metric (`task_c_weighted_triangle.py`)

Separately from how S3's road-repair *ranking* is produced, a second question was
raised: does explicitly weighting "critical" assets in the *evaluation* metric
(not just the ranking method) matter for whether the O–D representation looks
favorable? This is implemented as a new, additional metric computed **post hoc**
from each run's existing `event_log` (no changes to
`resilience_measurement.run_model_multi`, no re-simulation):

- `weighted_power_func(t)`: same functional/broken-bus logic as
  `eval_power_resilience`, but each bus is counted by a weight instead of
  uniformly by 1/33. Designated critical buses get `bus_weight_multiplier`;
  everyone else gets weight 1.
  - `CriticalWeightConfig.critical_buses = (8, 17)` (same set as the O–D
    destinations, for consistency), `bus_weight_multiplier = 3.0`.
- `shelter_access_func(t)`: shortest-path time from the depot to the designated
  shelter node at the current TAP-B snapshot, normalized by that same run's own
  undisrupted baseline (`run_dir/baseline_s.txt`, already written by
  `run_model_multi` unconditionally).
  - `CriticalWeightConfig.shelter_node = 24`, `depot_node = 1`.
- `weighted_triangle_area = ∫ [w_road·(1-road_func) + w_power·(1-weighted_power_func)
  + w_shelter·(1-shelter_access_func)] dt`, with `w_road = w_power = w_shelter = 1.0`
  by default — an equal-weight extension of the base simulator's own
  `w_road = w_power = 1` convention to three terms, not independently
  re-derived.

This is reported **alongside**, not instead of, the standard `triangle_area`
already used elsewhere in this dissertation. `task_c_runner.py` computes both for
every strategy's run (S0–S3), from the same simulation, so nothing about the
main efficiency comparison already run needs to be re-litigated — only reinterpreted
if the weighted version tells a materially different story.

## Two supplemental questions being tested together

Per discussion, before touching the paper draft again (the v1 draft is kept as
`OD_Representation_Paper_Draft_OLD.docx` / `build_od_paper_OLD.py` for reference),
the plan is to run the corrected v2 S3 design and look at **both** metrics before
deciding how to write this up:

1. Does the corrected (fixed, damage-independent) O–D representation show a
   resilience-triangle (standard, unweighted) advantage over S0–S2 on its own?
2. If not, does it show an advantage once critical-bus and shelter accessibility
   are explicitly weighted more heavily in the evaluation (`weighted_triangle_area`)?

Either outcome is usable; which one is true changes how Task C's contribution
should be framed.
